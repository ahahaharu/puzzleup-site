Выполни пункт роадмапа **$0** из `docs/roadmap.md` от начала до открытого PR. Режим: `$1` (если `auto` – без остановки на согласование плана; иначе – обязательная остановка после плана).

Разделы 1–2 только читают – их можно выполнять в режиме плана (модель `opusplan` планирует на Opus, а реализует на Sonnet). Ветка создаётся в разделе 3, после согласования.

## 1. Подготовка (только чтение)

1. `git status` – рабочее дерево должно быть чистым. Если нет – остановись и спроси.
2. Найди пункт $0 в `docs/roadmap.md`: имя ветки и что входит.
3. Проверь, есть ли ветка: `git fetch -q && git branch -a --list '*<ветка>'`. Если есть – это продолжение: прочитай описание PR (`gh pr view <ветка>`) и продолжи с раздела «Осталось»; изменения ветки – `git diff develop...origin/<ветка> --stat`.

## 2. План

1. Читай только то, что относится к пункту:
   - ТЗ – индекс `docs/spec/home/README.md` и `docs/spec/tutor-page/README.md`, затем только файлы нужных разделов;
   - макеты блока из `docs/design/` (по `docs/design/README.md`);
   - `docs/design-system.md`, `docs/architecture.md`, `docs/data-model.md`, `docs/decisions.md` – сначала `grep -n '^#'`, затем нужные разделы через Read с `offset`/`limit`.
2. Составь план:
   - что будет сделано, со ссылками на разделы ТЗ;
   - список файлов (создать / изменить);
   - какие тесты и на каком уровне;
   - новые зависимости и зачем;
   - вопросы и места, где ТЗ неоднозначно.
3. Если режим не `auto` – **остановись и покажи план** (в режиме плана – через ExitPlanMode). Жди «ок» или правок.
4. Если режим `auto`, но есть вопросы, без ответа на которые результат будет угадыванием, – всё равно остановись и спроси. Мелкие неясности реши сам и запиши в раздел «Решения» описания PR.

## 3. Реализация

1. Ветка: новая – `git checkout develop && git pull && git checkout -b <ветка из роадмапа>`; продолжение – `git checkout <ветка> && git pull`.
2. Работай маленькими шагами. После каждого логически цельного шага: `pnpm -s lint && pnpm -s typecheck && pnpm -s test --reporter=dot` → коммит по Conventional Commits на английском. Длинный вывод не нужен: при ошибке смотри только её.
3. Не используй `--no-verify`. Если хук упал – исправь причину.
4. Тексты – дословно из ТЗ. Визуал – по макету и токенам ДС.
5. Если появилось решение, которого нет в документах, допиши его в `docs/decisions.md` отдельным коммитом `docs(decisions): …`.
6. Если задача разрастается (контекст заканчивается, а сделана меньше половины), выполни шаги раздела 5 с пометкой «в работе» и предложи продолжить в новой сессии командой `/feature $0`.

## 4. Проверка

1. Сам: `pnpm -s build 2>&1 | tail -40` (статические `/` и `/tutors/[slug]` – ○ / ●, не ƒ); если затронуты `src/server` или БД – `pnpm -s test:int`. Непокрытое поведение – допиши тесты сам. Полный прогон (format, lint, typecheck, content:check, тесты, сборка, E2E, gitleaks, audit) делает CI.
2. Запусти агентов по очереди:
   1. `spec-reviewer` – всегда.
   2. `copy-checker` – если менялись тексты, контент, метатеги или тексты бота.
   3. `design-reviewer` – только если менялся внешний вид: новый блок или компонент, раскладка, стили, токены. Правки текста, логики, данных и тестов без изменения вёрстки – не повод.

   **Промпт агенту – только «Ветка `<ветка>`, пункт $0 роадмапа. Проверь по своей инструкции.»** Без пересказа реализации, списка файлов, своих выводов и «что уже проверено»: агент должен прийти к ним сам, иначе он примет ошибки основной сессии за данность.
3. Исправь все блокеры. Затем повтори проверку тем агентом, который их нашёл, – **продолжением того же агента** через SendMessage: «В ветке новые коммиты `<прошлый HEAD>..HEAD`. Проверь заново.» Не пиши, что и как исправлено. Документы он уже прочитал и не перечитывает. Новый агент – только если старого продолжить нельзя.
4. Замечания уровня «желательно» исправь, если это быстро, иначе вынеси в раздел «Осталось / идеи» PR.

## 5. PR

1. `git push -u origin <ветка>`.
2. Создай или обнови PR в `develop`: `gh pr create --base develop --fill-first` и затем `gh pr edit --body-file -` с телом по шаблону `.github/pull_request_template.md`, плюс разделы:
   - **Решения** – что решил сам и почему;
   - **Отчёты агентов** – итоги spec-reviewer, copy-checker, design-reviewer (одной строкой каждый + ссылки на скриншоты, если есть);
   - **Осталось** – если работа не закончена.
3. Дождись CI без потокового вывода: `gh pr checks --watch --fail-fast >/dev/null 2>&1; gh pr checks`. Если упало – `gh run view <id> --log-failed | tail -60`, исправь, запушь и проверь снова.
4. **Не мёрджи PR.** Слияние делает человек.

## 6. Итог

Коротко: ссылка на PR, что сделано, что проверить руками (на каких ширинах, какие сценарии), открытые вопросы. Последней строкой: «Перед следующим пунктом – `/clear`».

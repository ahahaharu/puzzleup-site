Выполни пункт роадмапа **$0** из `docs/roadmap.md` от начала до открытого PR. Режим: `$1` (если `auto` – без остановки на согласование плана; иначе – обязательная остановка после плана).

## 1. Подготовка

1. `git status` – рабочее дерево должно быть чистым. Если нет – остановись и спроси.
2. `git checkout develop && git pull`.
3. Найди пункт $0 в `docs/roadmap.md`: имя ветки и что входит. Если ветка уже существует (локально или в origin) – это продолжение: переключись на неё, прочитай описание открытого PR (`gh pr view`) и продолжи с раздела «Осталось».
4. Иначе `git checkout -b <ветка из роадмапа>`.

## 2. План

1. Прочитай всё, что относится к пункту: разделы `docs/spec/*`, файлы макетов из `docs/design/` (по `docs/design/README.md`), `docs/design-system.md`, `docs/architecture.md`, `docs/data-model.md`, `docs/decisions.md`.
2. Составь план:
   - что будет сделано, со ссылками на разделы ТЗ;
   - список файлов (создать / изменить);
   - какие тесты и на каком уровне;
   - новые зависимости и зачем;
   - вопросы и места, где ТЗ неоднозначно.
3. Если режим не `auto` – **остановись и покажи план**. Жди «ок» или правок.
4. Если режим `auto`, но есть вопросы, без ответа на которые результат будет угадыванием, – всё равно остановись и спроси. Мелкие неясности реши сам и запиши в раздел «Решения» описания PR.

## 3. Реализация

- Работай маленькими шагами. После каждого логически цельного шага: `pnpm lint && pnpm typecheck && pnpm test` → коммит по Conventional Commits на английском.
- Не используй `--no-verify`. Если хук упал – исправь причину.
- Тексты – дословно из ТЗ. Визуал – по макету и токенам ДС.
- Если появилось решение, которого нет в документах, допиши его в `docs/decisions.md` отдельным коммитом `docs(decisions): …`.
- Если задача разрастается (контекст заканчивается, а сделана меньше половины), выполни шаги раздела 5 с пометкой «в работе» и предложи продолжить в новой сессии командой `/feature $0`.

## 4. Проверка

1. Сам: `pnpm build` (статические `/` и `/tutors/[slug]` – ○ / ●, не ƒ); если затронуты `src/server` или БД – `pnpm test:int`. Непокрытое поведение – допиши тесты сам. Полный прогон (format, lint, typecheck, content:check, тесты, сборка, E2E, gitleaks, audit) делает CI.
2. Запусти агентов по очереди и исправь всё из блокеров:
   1. `spec-reviewer` – всегда.
   2. `copy-checker` – если менялись тексты, контент, метатеги или тексты бота.
   3. `design-reviewer` – только если менялся внешний вид: новый блок или компонент, раскладка, стили, токены. Правки текста, логики, данных и тестов без изменения вёрстки – не повод.

После исправлений повтори агента, который нашёл блокеры. Замечания уровня «желательно» исправь, если это быстро, иначе вынеси в раздел «Осталось / идеи» PR.

## 5. PR

1. `git push -u origin <ветка>`.
2. Создай или обнови PR в `develop`: `gh pr create --base develop --fill-first` и затем `gh pr edit --body-file -` с телом по шаблону `.github/pull_request_template.md`, плюс разделы:
   - **Решения** – что решил сам и почему;
   - **Отчёты агентов** – итоги spec-reviewer, copy-checker, design-reviewer (одной строкой каждый + ссылки на скриншоты, если есть);
   - **Осталось** – если работа не закончена.
3. Дождись CI: `gh pr checks --watch`. Если упало – исправь, запушь и проверь снова.
4. **Не мёрджи PR.** Слияние делает человек.

## 6. Итог

Коротко: ссылка на PR, что сделано, что проверить руками (на каких ширинах, какие сценарии), открытые вопросы.
